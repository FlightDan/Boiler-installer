# Installation preparation at 32% — 2026-11-01

## Confirmed failures

The reported local UI candidate reached component integration (02.01, 32%).
Its OXP3 model was `0.1.0-localtest.20261030.8`. The legacy maintenance loader
raised `Maintenance application differs from its staged manifest`. The package
builder had modified `oxp3_maintenance/components.py` and `input_profile.py`
without regenerating `payload/legacy/maintenance/manifest.json`. The outer
package inventory was valid, but the inner maintenance inventory was stale.

The password-enabled, three-volume guest startup command also exceeded the
interactive shell's physical input line capacity. Its echoed shutdown tail
was truncated to `pow`; the shell reported `pow: not found` and remained alive
after the integration failure. The host waited for guest exit until the task
was cancelled. The exported session had no deployment record: its recorded
failure occurred during preparation, before physical deployment.

## Changes

- The repair builder regenerates the inner maintenance inventory from final
  generated bytes before building the outer package inventory and ZIP. It
  still rejects missing or unexpected maintenance members. The runtime
  inventory check remains intact.
- The next generated model identity is `0.1.0-localtest.20261101.9`; historical
  packages and source locks remain intact.
- Guest startup commands use `&&` newline continuations within the enclosing
  subshell. Each physical line stays short while the full command is parsed
  before the password handshake runs. The shutdown tail is preserved.
- Targeted regressions exercise the actual maintenance loader with stale,
  regenerated and subsequently corrupted bytes, and missing/extra members.
  Windows command checks cover password/no-password and 1, 3 and 8 volumes.
